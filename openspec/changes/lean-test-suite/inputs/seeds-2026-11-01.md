# Seeds and Q&A — lean-test-suite (secondary; never groomed)

Captured 2026-11-01 from a conversation with the developer. The EPIC (`../proposal.md`) supersedes
this record but does not replace it.

## The developer's asks, in their words

1. "is there a better way of writing tests? … tell me what can be done to make the tests more about
   checking quality, and alignment towards the business goals, and capabilities, and what is meant to
   be implemented in this repo" (prompted by the suite growing from 478 to about 575 unit tests,
   mostly parametrised rows, during the namespace-prefixes work).
2. "what about consistent and unified way of managing fixtures and sample data? it becomes easy to
   establish expectations on the same sample data used over and over, no?"
3. "write a new epic with how you could improve and unify, but keep also guardrails up, and adopt a
   decent separation and fencing technique … try to eliminate redundancy, minimal necessary set of
   tests please, max coverage, max edge cases, work towards maxing maintainability"

## Codebase analysis (2026-10-31, master at 64276c1)

- Unit tests are grouped by module (`tests/unit/test_<layer>_<module>.py`), not by capability; no
  test names the requirement it proves.
- Spec ↔ Gherkin link is by count only: scenario titles in `openspec/specs/<cap>/spec.md` and
  `tests/features/<cap>.feature` differ (e.g. "Custom template package" vs "A custom template
  package"), and some exist on one side only.
- The same behaviour is tested two or three times: "rendering never queries" appears in
  `tests/unit/test_service_layer_report.py:58` and in two feature files; the steps "an endpoint that
  fails on any query" / "the endpoint was never queried" are defined twice
  (`tests/unit/steps/test_fingerprint_report_steps.py:69`, `test_profile_representations_steps.py:67`).
- Sample data is built three ways, with no `conftest.py`: raw dicts written inline in 9 test files;
  builders in `tests/unit/fakes.py` that return dicts; and `tests/test_data/profiles/sample-profile.json`,
  maintained by hand with no make target deriving it from `tests/test_data/*-source-ap.rdf`.
- Golden files (`tests/test_data/golden/`) compare text byte for byte; `UPDATE_GOLDEN=1` rewrites them.
  The SHACL golden test also validates the shapes against the source data — a quality check worth keeping.
- Gate: `--cov-fail-under=80` line coverage over `fingerprint`; no branch coverage, no mutation testing,
  no property-based tests; unit-tier network access is not blocked.
- `.importlinter` has `root_package = fingerprint`; the tests are not fenced.

## Q&A round 1 (2026-11-01)

| Question | Answer |
|---|---|
| What should "max coverage" gate on? | Branch + mutation: branch coverage 100% for `domain/`, 90% for the rest; a mutation score on `domain/` and `service_layer/`, reported and ratcheted (may only go up). |
| Which new dev-only dependencies may it add? | `mutmut` and `hypothesis`. Not `pytest-socket` (network blocking is done without it). |
| What fencing between test tiers? | Tier = layer + rules: `tests/unit/<layer>/` mirrors the package layers, the Gherkin tier holds capability behaviour, `tests/e2e/` the real store; import-linter contracts on the tests; no network in unit tests. |
| When does it run? | After the in-flight work: shape and plan now; implement once the namespace-prefixes work and `batched-collection` are merged. |
