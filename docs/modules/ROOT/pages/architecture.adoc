= Architecture
:description: Scope, structure and architecture decisions of rdf-fingerprinter.

This page records the architecture of rdf-fingerprinter: what it is for and how it is
structured. It describes release 2.0 (OpenSpec change `harden-fingerprinter`) and the additions of
2.1 (change `profile-representations`), marked _(2.1)_; where 1.x differed, a note says so.

== Purpose and scope

rdf-fingerprinter infers the *application profile* a knowledge graph actually follows. It reads
the data through a SPARQL endpoint, collects statistics per graph, class and property, derives
indicators from them (cardinalities, confidence, value types, hierarchy), and writes an HTML
report, the raw profile and, from 2.1, SHACL shapes, a PlantUML diagram and an application-profile
document. It is a Python library with a console script (`fingerprint`); it is not deployed as a
service.

In scope:: profiling any SPARQL 1.1 endpoint, read-only; the statistics and analytics model;
the HTML report; _(2.1)_ the saved profile and the SHACL, PlantUML and document representations.
Out of scope:: VoID and LLM tooling (`llm-schema-tools`); benchmarking (`benchmark-fingerprinter`);
batched collection (`batched-collection`); profiling RDF files; writing to the endpoint.

== Architectural drivers

[cols="1,3"]
|===
| Scale | Profiles large knowledge graphs (millions of instances per class) without one query
covering the whole graph.
| Portability | Any SPARQL 1.1 store; no store-specific SPARQL.
| Honesty | Every number states how precise it is; failures are visible and fail the run.
| Reuse | One profile feeds every representation without querying again (xref:decisions.adoc#ad-7[AD-7]).
| Trustworthy shapes | Generated constraints never claim more than the profile observed (xref:decisions.adoc#ad-10[AD-10]).
| Embeddability | Usable as a library inside other applications (rdf-fingerprinter-ws) and as a CLI.
|===

== L1 — System context

----
 Data steward ─────────uses──────▶ ┌───────────────────────┐ ──reads (SPARQL 1.1)──▶ SPARQL endpoint
 rdf-fingerprinter-ws ─embeds────▶ │   rdf-fingerprinter   │                          (any store)
                                   └───────────────────────┘
                                      │ writes        ▲ reads (2.1)
                                      ▼               │
                       output folder: report, profile.json, shapes, diagrams, document
----

Services offered::
* *Fingerprint an endpoint* — profile + report (xref:use-cases/ucw1.adoc#uc-w1[UC-W1]), through
  the `fingerprint` CLI and the function `generate_endpoint_fingerprint_report`.
* _(2.1)_ *Publish a fingerprint as an application profile* — SHACL, PlantUML, document from a
  profile (xref:use-cases/ucw2.adoc#uc-w2[UC-W2]), through `fingerprint --format` and the
  `fingerprint-gen-*` commands.

== L2 — Containers

rdf-fingerprinter has no runtime of its own: it runs inside the caller's Python process. The
containers around it are the *SPARQL endpoint* (external, read-only use) and the *output folder*
(files). Communication is synchronous HTTP to the endpoint and file writes to the folder. From 2.1
the output folder is also an input: `profile.json` is read back by the generators, which never
contact the endpoint.

== L3 — Components (inside the library)

[cols="1,2,2"]
|===
| Layer (package) | Responsibility | May import

| `fingerprint.entrypoints` (`cli`)
| Parse options, configure logging, call the service layer, map outcomes to exit codes 0 (clean), 1 (failures recorded), 2 (usage), 3 (endpoint unreachable), 4 (unexpected error). _(2.1)_ the `fingerprint-gen-*` commands and `--format`.
| service layer, adapters, domain

| `fingerprint.service_layer`
| Settings precedence; the collection algorithm (discovery, per-class queries, precision
escalation, concurrency); report rendering through eds4jinja2; the public function. _(2.1)_
`generators/`: the `Generator` base (visit hooks, serialize, check, write) and the SHACL,
PlantUML and document generators.
| adapters, domain

| `fingerprint.adapters`
| `SparqlPort` and its SPARQLWrapper implementation (timeout, retry, failure classes); the query
templates (`queries/*.rq`). _(2.1)_ `profile_file`: save and load `profile.json`.
| domain

| `fingerprint.domain`
| The profile model (generated from LinkML), IRI guard, all analytics
— pure functions, no I/O.
| nothing above it; no SPARQLWrapper, eds4jinja2 or click

| `fingerprint_report_templates`
| Packaged eds4jinja2 template packages: `fingerprint_report` and _(2.1)_ `shacl_shapes`,
`plantuml_diagram`, `profile_document`; render the analytics or the generator's view; issue no queries.
| —
|===

The layers are enforced by `.importlinter` (`make check-architecture`), including two forbidden
contracts: the generated module imports no project code, and the domain imports no I/O library.

NOTE: 1.x had only `service_layer` and `entrypoints`; its statistics were computed by SPARQL inside
the templates.

=== Data flow

----
 CLI / caller ──settings──▶ collect() ──SPARQL──▶ endpoint
                               │ profile run (fingerprint_stats)
                               ├──────────▶ save_profile() ──▶ profile.json          (2.1)
                               ▼                                   │ load_profile()
                           analyse()  (domain, pure) ◀─────────────┘ (+ threshold)
                               │ analytics (fingerprint_analytics)
                   ┌───────────┴────────────────┐
                   ▼                            ▼
           render_report()            Generator.write()                        (2.1)
           ──eds4jinja2──▶ main.html  visit hooks → view ──eds4jinja2──▶ text
                                      ──check──▶ shapes-*.ttl, diagram-*.puml, profile.html
----

=== Profile model

The model is LinkML, namespace `fp: https://data.meaningfy.ws/fingerprint/`, in two schemas
under `model/`:

* `fingerprint_stats` — raw observations only: run and settings, graphs, classes with instance
  counts and the precision mode used, cardinality histograms, value partitions, co-types,
  subclass edges, incoming links, failures. Reuses VoID terms where the meaning matches.
* `fingerprint_analytics` — extends each raw class with computed indicators (min/max/mean,
  confidence, cardinality label, value-type purity, diversity, parents, own/inherited, …).

Rules for the generated code (P-10): `make generate-models` writes
`fingerprint/domain/generated/profile.py` with a do-not-edit banner; `make check-models` (part of
`make check-all`) fails when it is out of date; the generated classes are frozen and reject
unknown fields; Ruff excludes the folder; import-linter keeps it free of project imports.
