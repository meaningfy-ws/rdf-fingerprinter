= Architecture
:description: Scope, structure and architecture decisions of rdf-fingerprinter.

This page records the architecture of rdf-fingerprinter: what it is for and how it is
structured, as of release 2.1. The collection, analytics and report came with 2.0 (OpenSpec change
`harden-fingerprinter`), the saved profile and the representations with 2.1 (change
`profile-representations`); where 1.x differed, a note says so.

* xref:use-cases/index.adoc[Use cases] — the behavioural contract (White) and its realisations (Blue).

== Purpose and scope

rdf-fingerprinter infers the *application profile* a knowledge graph actually follows. It reads
the data through a SPARQL endpoint, collects statistics per graph, class and property, derives
indicators from them (cardinalities, confidence, value types, hierarchy), and writes an HTML
report, the raw profile and, from 2.1, SHACL shapes, a PlantUML diagram and an application-profile
document. It is a Python library with a console script (`fingerprint`); it is not deployed as a
service.

In scope:: profiling any SPARQL 1.1 endpoint, read-only; the statistics and analytics model;
the HTML report; the saved profile and the SHACL, PlantUML and document representations.
Out of scope:: VoID and LLM tooling (`llm-schema-tools`); benchmarking (`benchmark-fingerprinter`);
batched collection (`batched-collection`); profiling RDF files; writing to the endpoint.

== Architectural drivers

[cols="1,3"]
|===
| Scale | Profiles large knowledge graphs (millions of instances per class) without one query
covering the whole graph.
| Portability | Any SPARQL 1.1 store; no store-specific SPARQL.
| Honesty | Every number states how precise it is; failures are visible and fail the run.
| Reuse | One profile feeds every representation without querying again (xref:decisions.adoc#ad-7[AD-7]).
| Trustworthy shapes | Generated constraints never claim more than the profile observed (xref:decisions.adoc#ad-10[AD-10]).
| Embeddability | Usable as a library inside other applications (rdf-fingerprinter-ws) and as a CLI.
|===

== L1 — System context

----
 Requester: data steward ──uses──▶ ┌───────────────────────┐ ──reads (SPARQL 1.1)──▶ SPARQL endpoint
 Requester: embedding app ─embeds─▶ │   rdf-fingerprinter   │                          (any store)
                                   └───────────────────────┘
                                      │ writes        ▲ reads
                                      ▼               │
                       output folder: report, profile.json, shapes, diagrams, document
----

Services offered::
* *Fingerprint an endpoint* — profile + report (xref:use-cases/ucw1.adoc[UC-W1]).
* *Publish a fingerprint as an application profile* — SHACL shapes, a class diagram and a
  specification document from a profile (xref:use-cases/ucw2.adoc[UC-W2]).

Actors and systems are those of the xref:glossary.adoc#actors-and-stakeholders[Glossary]. The
interfaces that offer these services are listed at L3.

== L2 — Containers

[cols="1,2,2"]
|===
| Container | Responsibility | Interaction

| *rdf-fingerprinter* (system under design) | Profiles, analyses and renders. Has no runtime of its own: it runs inside the caller's process (a shell or an embedding application). | —
| *SPARQL endpoint* (external) | Holds the data. | read-only, synchronous request–response from rdf-fingerprinter
| *Output folder* (files) | Holds the outputs; also the saved profile, read back for later regenerations. | written by rdf-fingerprinter; `profile.json` read back
|===

From 2.1 the generators never contact the endpoint (xref:decisions.adoc#ad-7[AD-7]).

== L3 — Components (inside the library)

[cols="1,2,2"]
|===
| Layer (package) | Components | May import

| `fingerprint.entrypoints`
| Command line: the `fingerprint` command; `--format` and the `fingerprint-gen-*` commands.
Parses options, configures logging, maps outcomes to exit codes.
| service layer, adapters, domain

| `fingerprint.service_layer`
| Public function (`generate_endpoint_fingerprint_report`); Report service; Settings resolver;
Collector; Generators (one per format, building its view) and the Representations service,
which the generator commands call.
| adapters, domain

| `fingerprint.adapters`
| SPARQL client (`SparqlPort` and its SPARQLWrapper implementation) and the query templates;
 Template renderer (eds4jinja2 rendering, Turtle check, file writes, shared by the report and
the generators), Profile store (`profile.json`), setting sources (environment, config file).
| domain

| `fingerprint.domain`
| Profile model (generated from LinkML); Analyser; IRI rules (SPARQL and, from 2.1, Turtle).
Pure, no I/O.
| nothing above it; not SPARQLWrapper, eds4jinja2, jinja2, rdflib or click (enforced)

| `fingerprint_report_templates`
| Template packages: `fingerprint_report`; `shacl_shapes`, `plantuml_diagram`,
`profile_document`. Lay out what they are given; issue no queries.
| —
|===

Component names are those of the xref:glossary.adoc#components[Glossary], which maps each to its
module. The layers are enforced by `.importlinter` (`make check-architecture`): the layer order, a
generated model that imports no project code, a domain that imports no SPARQLWrapper, eds4jinja2,
jinja2, rdflib or click, and a service layer that imports no jinja2, eds4jinja2, rdflib or SPARQLWrapper itself (`allow_indirect_imports = True`: it may reach them only through adapters, as `handlers` reaches SPARQLWrapper through the default SPARQL client).

NOTE: 1.x had only `service_layer` and `entrypoints`; its statistics were computed by SPARQL inside
the templates. In 2.0 report rendering and the setting sources sat in the service layer; 2.1 moved
them to adapters (xref:decisions.adoc#ad-4[AD-4]).

The dynamic view — how a run moves through these components — is in
xref:how-it-works.adoc#data-flow[How it works].

== L4 — Key abstractions

[cols="1,3"]
|===
| Abstraction | Contract

| `SparqlPort` | `select(query) -> rows`, `ask(query) -> bool`; raises one of the error classes of xref:how-it-works.adoc#failure-classes[How it works].
| `ProfileRun`, `ProfileAnalytics` | The generated, frozen profile model (below).
| `TemplateRenderer` | `render(package, *, view, config, autoescape) -> str`; `write(folder, texts, check) -> list[Path]`, checking every text before writing any; `prefixes`. The port generators and the report render through; declared in the service layer, implemented by the template renderer adapter (`SparqlPort` is declared beside its adapter, a 2.0 choice kept).
| `Generator` | `visit_graph` / `visit_class` / `visit_property` build the view; `serialize()` returns file name → text (xref:decisions.adoc#ad-8[AD-8]).
| Exit codes | 0 clean, 1 failures recorded, 2 usage error, 3 endpoint unreachable at the start, 4 unexpected error.
|===

=== Profile model

The model is LinkML, namespace `fp: https://data.meaningfy.ws/fingerprint/`, in two schemas
under `model/`:

* `fingerprint_stats` — raw observations only: run and settings, graphs, classes with instance
  counts and the precision mode used, cardinality histograms, value partitions, co-types,
  subclass edges, incoming links, failures. Reuses VoID terms where the meaning matches.
* `fingerprint_analytics` — extends each raw class with computed indicators (min/max/mean,
  confidence, cardinality label, value-type purity, diversity, parents, own/inherited, …).

Rules for the generated code (P-10): `make generate-models` writes
`fingerprint/domain/generated/profile.py` with a do-not-edit banner; `make check-models` (part of
`make check-all`) fails when it is out of date; the generated classes are frozen and reject
unknown fields; Ruff excludes the folder; import-linter keeps it free of project imports.
