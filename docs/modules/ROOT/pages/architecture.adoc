= Architecture
:description: Scope, structure and architecture decisions of rdf-fingerprinter.

This page records the minimal architecture of rdf-fingerprinter: what it is for, how it is
structured, and the decisions that shape it. It describes the *target* architecture of release
2.0, planned in the OpenSpec change `harden-fingerprinter`; where 1.0 differs, a note says so.
Decision ids `DEC-n` and `P-n` refer to that change (`openspec/changes/harden-fingerprinter/`).

== Purpose and scope

rdf-fingerprinter infers the *application profile* a knowledge graph actually follows. It reads
the data through a SPARQL endpoint, collects statistics per graph, class and property, derives
indicators from them (cardinalities, confidence, value types, hierarchy), and writes an HTML
report. It is a Python library with a console script (`fingerprint`); it is not deployed as a
service.

In scope:: profiling any SPARQL 1.1 endpoint, read-only; the statistics and analytics model;
the HTML report.
Out of scope:: other representations (SHACL, PlantUML, ReSpec, VoID — change
`profile-representations`); LLM tooling (`llm-schema-tools`); benchmarking
(`benchmark-fingerprinter`); writing to the endpoint.

== Architectural drivers

[cols="1,3"]
|===
| Scale | Must profile large knowledge graphs (millions of instances per class) without one query
covering the whole graph.
| Portability | Any SPARQL 1.1 store; no store-specific SPARQL.
| Honesty | Every number states how precise it is; failures are visible and fail the run.
| Reuse | One profile feeds the report now and further representations later, without querying again.
| Embeddability | Usable as a library inside other applications (rdf-fingerprinter-ws) and as a CLI.
|===

== L1 — System context

----
 Data steward / developer ──uses──▶ rdf-fingerprinter (library + CLI)
                                         │  reads (SPARQL 1.1 SELECT/ASK over HTTP)
                                         ▼
                                    SPARQL endpoint (any store)
                                         │
 rdf-fingerprinter-ws ──embeds──▶ rdf-fingerprinter ──writes──▶ report folder (HTML)
----

Services offered:: *Fingerprint an endpoint* (profile + HTML report), through the
`fingerprint` CLI and the function `generate_endpoint_fingerprint_report`.

== L2 — Containers

rdf-fingerprinter has no runtime of its own: it runs inside the caller's Python process. The
containers around it are the *SPARQL endpoint* (external, read-only use) and the *output folder*
(files). Communication is synchronous HTTP to the endpoint and file writes to the folder.

== L3 — Components (inside the library)

[cols="1,2,2"]
|===
| Layer (package) | Responsibility | May import

| `fingerprint.entrypoints` (`cli`)
| Parse options, configure logging, call the service layer, map outcomes to exit codes 0 (clean), 1 (failures recorded), 3 (endpoint unreachable), 4 (unexpected error).
| service layer, adapters, domain

| `fingerprint.service_layer`
| Settings precedence; the collection algorithm (discovery, per-class queries, precision
escalation, concurrency); report rendering through eds4jinja2; the public function.
| adapters, domain

| `fingerprint.adapters`
| `SparqlPort` and its SPARQLWrapper implementation (timeout, retry, failure classes); the query
templates (`queries/*.rq`).
| domain

| `fingerprint.domain`
| The profile model (generated from LinkML), IRI guard, merge of partial results, all analytics
— pure functions, no I/O.
| nothing above it; no SPARQLWrapper, eds4jinja2 or click

| `fingerprint_report_templates`
| Packaged eds4jinja2 templates; render the analytics passed in the context; issue no queries.
| —
|===

The layers are enforced by `.importlinter` (`make check-architecture`), including two forbidden
contracts: the generated module imports no project code, and the domain imports no I/O library.

NOTE: 1.0 has only `service_layer` and `entrypoints`; its statistics are computed by SPARQL inside
the templates.

=== Data flow

----
 CLI / caller ──settings──▶ collect() ──SPARQL──▶ endpoint
                               │ raw statistics (fingerprint_stats)
                               ▼
                           analyse()  (domain, pure)
                               │ analytics (fingerprint_analytics)
                               ▼
                       render_report() ──eds4jinja2──▶ main.html
----

=== Profile model

The model is LinkML, namespace `fp: https://data.meaningfy.ws/fingerprint/`, in two schemas
under `model/`:

* `fingerprint_stats` — raw observations only: run and settings, graphs, classes with instance
  counts and the precision mode used, cardinality histograms, value partitions, co-types,
  subclass edges, incoming links, failures. Reuses VoID terms where the meaning matches.
* `fingerprint_analytics` — extends each raw class with computed indicators (min/max/mean,
  confidence, cardinality label, value-type purity, diversity, parents, own/inherited, …).

Rules for the generated code (P-10): `make generate-models` writes
`fingerprint/domain/generated/profile.py` with a do-not-edit banner; `make check-models` (part of
`make check-all`) fails when it is out of date; the generated classes are frozen and reject
unknown fields; Ruff excludes the folder; import-linter keeps it free of project imports.

== Architecture decisions

=== L1 — Context

[#ad-1]
==== AD-1 Profile from the data, through any SPARQL 1.1 endpoint, read-only

Context:: Profiles must reflect what the data *does*, on any store, without access beyond
querying.
Options:: (a) portable SPARQL 1.1 over HTTP; (b) store-specific SPARQL or native access
(Virtuoso JDBC, QLever variants), as void-generator does; (c) load dumps locally.
Decision:: (a). Statistics come from instance data, not from a declared ontology; only `SELECT`
and `ASK` are sent (DEC-5).
Consequences:: Works on every compliant store; cannot use store shortcuts, so cost is bounded by
query design (AD-3), not by engine tricks.
Confirmation:: e2e tests on Oxigraph; no store-specific syntax in `adapters/queries/`.

[#ad-2]
==== AD-2 A library with a CLI, not a service

Context:: Profiling is embedded by other systems (rdf-fingerprinter-ws) and run ad hoc.
Options:: (a) Python library + console script; (b) a deployed web service.
Decision:: (a); the service lives in rdf-fingerprinter-ws.
Consequences:: No runtime, no deployment; the public function's signature is a compatibility
contract (kept from 1.x).
Confirmation:: `pyproject.toml` (`fingerprint` script); unit test of the 1.x call.

=== L2 — Runtime and interaction

[#ad-3]
==== AD-3 Bounded work per query: staged discovery, class-scoped queries, precision escalation

Context:: One whole-graph aggregate per class (1.0) times out on large graphs; so does one global
class × property aggregate.
Options:: (a) staged discovery + per-class queries scoped to the class's instances, with
exact → batched → first-N escalation on timeout; (b) one global aggregate; (c) client-side
counting of every triple (sheXer, QSE style).
Decision:: (a) (DEC-2, DEC-3, DEC-10); classes run concurrently, biggest first.
Consequences:: Cost grows with instances read, not classes × graph size; precision is stored per
class; first-N results are biased to the store's row order and labelled as such.
Confirmation:: query texts contain the class inside the subject source; escalation scenarios in
`statistics-collection` spec.

=== L3 — Components

[#ad-4]
==== AD-4 Onion layers with a SPARQL port

Context:: The statistics logic must be testable without a store and isolated from I/O.
Options:: (a) cosmic-python layers, `SparqlPort` injected into the service layer; (b) logic in
templates (1.0).
Decision:: (a) (DEC-1, DEC-7).
Consequences:: Unit tests use a fake port; adding another SPARQL client touches only adapters.
Confirmation:: `.importlinter` contracts; `make check-architecture`.

[#ad-5]
==== AD-5 LinkML profile model as the contract: raw statistics and analytics, generated read-only

Context:: The report and later representations must read the same numbers.
Options:: (a) LinkML schemas, raw + analytics, generated Pydantic; (b) hand-written dataclasses.
Decision:: (a) (DEC-8, P-10). Analytics are always derived, never collected.
Consequences:: One contract for every consumer; a codegen step and a sync check; LinkML only at
development time, Pydantic at runtime.
Confirmation:: `make check-models`; frozen-model test.

[#ad-6]
==== AD-6 eds4jinja2 renders from the model; templates do not query

Context:: Custom templates exist in the wild; 1.0 templates embed SPARQL.
Options:: (a) keep eds4jinja2 as the renderer and pass the analytics in the context; (b) plain
Jinja2.
Decision:: (a) (DEC-6).
Consequences:: Custom templates keep working (eds4jinja2 fetchers still available); the default
template becomes query-free.
Confirmation:: report test with a SPARQL client that fails on any call.
