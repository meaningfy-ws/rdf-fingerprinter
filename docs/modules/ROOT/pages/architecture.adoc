= Architecture
:description: Scope, structure and architecture decisions of rdf-fingerprinter.

This page records the architecture of rdf-fingerprinter: what it is for and how it is
structured, as of release 3.5. The collection, analytics and report came with 2.0 (OpenSpec change
`harden-fingerprinter`), the saved profile and the representations with 2.1 (change
`profile-representations`), readable output with 3.0, pitfall scans with 3.1 (`pitfall-scans`),
schemas for language models with 3.2 to 3.4 (`llm-schema-tools`, `llm-schema-split`) and reified
relations with 3.5 (`singleton-property-pattern`); where 1.x differed, a note says so.
xref:comparison.adoc[Comparison] places it among other profilers.

== Purpose and scope

rdf-fingerprinter infers the *application profile* a knowledge graph actually follows. It reads
the data through a SPARQL endpoint, collects statistics per graph, class and property, derives
indicators from them (cardinalities, confidence, value types, hierarchy), and writes an HTML
report, the raw profile and, from 2.1, SHACL shapes and PlantUML diagrams; from 3.1 it can also scan
for modelling pitfalls, from 3.2 it writes schemas for language models (a pattern schema and
enriched ShExC), and from 3.5 it folds reifications into the relations they stand for. It is a Python library with a console script (`fingerprint`); it is not deployed as a
service.

In scope:: profiling any SPARQL 1.1 endpoint, read-only; the statistics and analytics model;
the HTML report; the saved profile and the SHACL, ShExC, PlantUML, pattern-schema and pitfall
representations; pitfall scans; reified relations.
Out of scope:: VoID output; answering questions with a language model (the fingerprinter writes
the schema, not the prompts); benchmarking (`benchmark-fingerprinter`); batched collection
(`batched-collection`); profiling RDF files directly (`make scan-files` loads them into a local
Oxigraph for pitfall scans); writing to the endpoint.

== Architectural drivers

[cols="1,3"]
|===
| Scale | Profiles large knowledge graphs (millions of instances per class) without one query
covering the whole graph.
| Portability | Any SPARQL 1.1 store; no store-specific SPARQL.
| Honesty | Every number states how precise it is; failures are visible and fail the run.
| Reuse | One profile feeds every representation without querying again (xref:decisions.adoc#ad-7[AD-7]).
| Trustworthy shapes | Generated constraints never claim more than the profile observed (xref:decisions.adoc#ad-10[AD-10]).
| Embeddability | Usable as a library inside other applications (rdf-fingerprinter-ws) and as a CLI.
|===

== L2 — Containers

[cols="1,2,2"]
|===
| Container | Responsibility | Interaction

| *rdf-fingerprinter* (system under design) | Profiles, analyses and renders. Has no runtime of its own: it runs inside the caller's process (a shell or an embedding application). | —
| *SPARQL endpoint* (external) | Holds the data. | read-only, synchronous request–response from rdf-fingerprinter
| *Output folder* (files) | Holds the outputs; also the saved profile, read back for later regenerations. | written by rdf-fingerprinter; `profile.json` read back
|===

From 2.1 the generators never contact the endpoint (xref:decisions.adoc#ad-7[AD-7]).

== L3 — Components (inside the library)

[cols="1,2,2"]
|===
| Layer (package) | Components | May import

| `fingerprint.entrypoints`
| Command line: the `fingerprint` command; `--format` and the `fingerprint-gen-*` commands.
Parses options, configures logging, maps outcomes to exit codes.
| service layer, adapters, domain

| `fingerprint.service_layer`
| Library entry (`fingerprint_report`); Settings resolver; Collector; Prefix resolver (the
namespace table); Collector, with the reification probes and the pitfall scan; Generators (one
per format, building its view; the report page is the document generator's) and the
Representations service, which the generator commands call.
| adapters, domain

| `fingerprint.adapters`
| SPARQL client (`SparqlPort` and its HTTP implementation, rdflib reading the results) and the
query templates; Template renderer (eds4jinja2 rendering, Turtle check, file writes, shared by the
report and the generators), Profile store (`profile.json`), Config resolver (environment, config
file), Pitfall catalogue and Reification catalogue (the packaged and user `.rq` checks and
templates, parsed before any query), Ontology file (labels for the pattern schema).
| domain

| `fingerprint.domain`
| Profile and views models (generated from LinkML); Analyser; IRI rules (SPARQL and, from 2.1,
Turtle); namespace filters; pattern and ShEx views; pitfall levels; reification folding. Pure, no I/O.
| nothing above it; not eds4jinja2, jinja2, rdflib or click (enforced)

| `fingerprint_report_templates`
| Template packages: `fingerprint_report`; `shacl_shapes`, `shex_schema`, `plantuml_diagram`,
`pattern_schema`, `pitfalls_tsv`. Lay out what they are given; issue no queries.
| —
|===

Component names are those of the xref:glossary.adoc#components[Glossary], which maps each to its
module. The layers are enforced by `.importlinter` (`make check-architecture`): the layer order, a
generated models that import no project code, a domain that imports no eds4jinja2, jinja2, rdflib
or click, and a service layer that imports no jinja2, eds4jinja2 or rdflib itself
(`allow_indirect_imports = True`: it may reach them only through adapters, as `handlers` reaches
rdflib through the default SPARQL client). One exception is declared: collection reads the client's
rdflib result rows and tells blank nodes by their term class.

The package root, `fingerprint/__init__.py`, holds the configuration: `config`, a
`FingerprintConfig` whose values each read an `RDF_FINGERPRINTER_*` variable through the config
resolver when accessed, never at import (xref:decisions.adoc#ad-12[AD-12]).

NOTE: 1.x had only `service_layer` and `entrypoints`; its statistics were computed by SPARQL inside
the templates. In 2.0 report rendering and the setting sources sat in the service layer; 2.1 moved
them to adapters (xref:decisions.adoc#ad-4[AD-4]).

The dynamic view — how a run moves through these components — is in
xref:how-it-works.adoc#data-flow[How it works].

== L4 — Key abstractions

[cols="1,3"]
|===
| Abstraction | Contract

| `SparqlPort` | `select(query) -> list[ResultRow]` (rdflib rows of `URIRef`, `BNode` and typed `Literal`; an unbound variable is `None`), `ask(query) -> bool`; raises one of the error classes of xref:how-it-works.adoc#failure-classes[How it works].
| `ProfileRun`, `ProfileAnalytics` | The generated, frozen profile model (below).
| `TemplateRenderer` | `render(package, outputs, *, conf, autoescape) -> list[RenderedDocument]` (in memory); `make(package, outputs, *, folder, conf, check, autoescape) -> list[Path]`, checking every text before writing any; `outputs` are (file name, view) pairs; `prefixes`. Implemented on eds4jinja2 2.1's `render_documents` / `make_documents`. The port generators and the report render through; declared in the service layer, implemented by the template renderer adapter (`SparqlPort` is declared beside its adapter, a 2.0 choice kept).
| `Generator` | pre-order `visit_graph` / `visit_class` (return `False` to skip), `visit_property` (a property's view), post-order `end_class` / `end_graph` (the frozen class and graph views); `serialize()` returns `list[RenderedDocument]`; formats keyed by `RepresentationFormat`, options a `GeneratorOptions` (xref:decisions.adoc#ad-8[AD-8]).
| `FingerprintConfig` | `config.<value>` reads its `RDF_FINGERPRINTER_*` variable on access; `validate()` reads them all and names the first bad one (xref:decisions.adoc#ad-12[AD-12]).
| Exit codes | 0 clean, 1 failures recorded, 2 usage error, 3 endpoint unreachable at the start, 4 unexpected error, 5 pitfalls at the `--fail-on` level.
|===

=== Profile model

The model is LinkML, namespace `fp: https://data.meaningfy.ws/fingerprint/`, in three schemas
under `model/`. It describes the fingerprinter's own data (what a run observed, what the analyser
derives, what the templates receive), not the profiled dataset. LinkML generates only these Python
classes and the JSON Schema of `profile.json`; the SHACL, ShExC, PlantUML and other outputs are
written by the fingerprinter's generators and templates (xref:decisions.adoc#ad-8[AD-8]).
The schemas:

* `fingerprint_stats` — raw observations only: run and settings, graphs, classes with instance
  counts and the precision mode used, cardinality histograms, value partitions, co-types,
  subclass edges, incoming links, failures. Reuses VoID terms where the meaning matches.
* `fingerprint_analytics` — extends each raw class with computed indicators (min/max/mean,
  confidence, cardinality label, value-type purity, diversity, parents, own/inherited, …).
* `fingerprint_views` — what the representation templates receive: shapes graphs, diagram graphs,
  the profile document, `RenderedDocument`, `GeneratorOptions` and the enums of formats,
  severities and diagram members.

Values are these classes and enums throughout the code, never composed dicts; the check
`tests/guards/test_no_composed_dicts.py` fails on a new one unless its line gives a reason
(`# dict-ok: <reason>`, kept for library boundaries, prefix tables and lookup indexes).

Rules for the generated code (P-10): `make generate-models` writes
`fingerprint/domain/profile.py` and `fingerprint/domain/views.py` with a do-not-edit banner; `make check-models` (part of
`make check-all`) fails when it is out of date; the generated classes are frozen and reject
unknown fields; Ruff excludes the module; import-linter keeps it free of project imports.
