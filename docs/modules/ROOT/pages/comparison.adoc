= Comparison
:description: How rdf-fingerprinter compares with seven open-source tools that profile RDF data or infer shapes from it, feature by feature.

Several open-source tools infer what an RDF dataset holds: its classes, how their properties are
used, and the shapes the data follows. This page compares rdf-fingerprinter 3.5 with seven of them,
feature by feature, in groups. Each group opens with what matters and how the tools differ; the
table under it holds the detail.

How the facts were gathered:: The other tools' source code was read, not run: shallow clones taken
on 2026-10-31, audited feature by feature on 2026-11-08 against their code, queries and READMEs.
"No" means a search of the source found nothing, not that the feature was proven absent; a tool may
have changed since. Corrections are welcome as issues.
Legend:: ✓ yes · ◐ partly (the cell says how) · ✗ no · ? unknown.

How to read it: the endpoint is on the left; the tools in the top panel ask it to count and get
small answers back, the tools in the bottom panel pull triples across and count them themselves.
rdf-fingerprinter is teal; QSE appears in both panels because it has a mode of each kind.

Push:: The endpoint aggregates and returns small answers. Little crosses the network, but each
query must finish within the endpoint's time limit, so these tools differ in how they keep queries
small. rdf-fingerprinter, SHACL Play, void-generator, QSE and RDF2Graph all bind the class inside the
pattern (`?s a <C>`), so the store touches only that class's instances
(xref:decisions.adoc#ad-3[AD-3]).
Pull:: The client reads triples and counts them itself. Counts are exact and the endpoint does
little work, but the whole graph, or a crawl or sample of it, crosses the network. sheXer reads an
endpoint by asking for the triples of each instance; shaclgen and LODStats read files only (LODStats'
SPARQL mode counts nothing but the total number of triples).

== Input and access

All five endpoint tools send only reads to the data, but they differ in reach. rdf-fingerprinter
works with any SPARQL 1.1 store, profiles every named graph and accepts HTTP Basic authentication;
void-generator matches it on named graphs and adds store-specific speed (Virtuoso JDBC, QLever query
variants); QSE needs GraphDB. Files are where the pull tools are strong: sheXer streams very large
N-Triples and Turtle files, and rdf-fingerprinter reads none directly.

== Discovery: classes, hierarchy, links

Every tool lists classes; they differ in what they do with the hierarchy. rdf-fingerprinter reads
the declared `rdfs:subClassOf` statements, finds implied parents from the other types instances
carry, and marks each property own, inherited or refined. RDF2Graph goes furthest in another
direction: it lifts shared properties up to the common parent. SHACL Play uses co-occurring classes
to choose the most precise `sh:class`.

== Statistics per class and property

This is where profilers differ most. Most decide only two facts per property: is it required, and
is it single-valued. rdf-fingerprinter keeps the whole cardinality histogram, from which it gives
minimum, maximum and mean values per instance, a cardinality label (`1`, `?`, `+`, `*`) and a
confidence: "one value for 98 % of instances", not just "optional". sheXer also keeps histograms and
a conformance ratio; QSE gives support and confidence per constraint. rdf-fingerprinter also records
language tags, top values and value ranges, which most others leave out.

== Scale and robustness

On a large graph some query will time out. What happens then? rdf-fingerprinter reads the class
again from its first N instances, labels every number from it "first N of M", and if that fails too,
records the failure, carries on and exits 1. SHACL Play also falls back to a labelled sample.
void-generator scales by concurrency and store shortcuts instead, and is the only tool besides
RDF2Graph that keeps work from an interrupted run.

== Outputs for people

Only rdf-fingerprinter and SHACL Play produce a document a person reads from start to finish.
rdf-fingerprinter's report is one static HTML page about the *data*: namespaces, taxonomy, a section
per class, every failure and pitfall. SHACL Play documents the *shapes*, as HTML or PDF with charts.
Both draw PlantUML diagrams; RDF2Graph builds a Cytoscape network.

== Outputs for agents

A language model that writes SPARQL needs the schema in its context, compact and labelled. None of
the other seven writes for that reader. rdf-fingerprinter writes a pattern schema, compact
`(:Class) -property-> (:Target)` lines with statistics, plus a glossary of labels and definitions
and enriched ShExC (xref:llm-schema.adoc[Schemas for LLMs]).

== Outputs for machines

Shapes and statistics in standard formats. rdf-fingerprinter writes SHACL graded by severity, so
validated against the data it came from it reports no violation; QSE prunes by support and

rdf-fingerprinter does not.

== Quality and semantics

Profiling shows what the data holds; these features judge it. rdf-fingerprinter runs 28 pitfall
checks (25 from the OOPS! catalogue) and can fail a CI job on them. RDF2Graph reports three data
errors (untyped subjects, untyped targets, a class used as a predicate). Reification is the other
gap in the field: statements about statements show up in most profiles as noise, and only
rdf-fingerprinter folds them into the relations they stand for (xref:reifications.adoc[Reified
Relations]); sheXer handles Wikidata qualifiers, RDF2Graph skips `rdf:subject`, `rdf:predicate` and
`rdf:object`.

== What only rdf-fingerprinter does

Among these eight tools, only rdf-fingerprinter:

* writes a schema for a language model (pattern schema, glossary, enriched ShExC);
* folds reifications into the relations they stand for;
* runs a catalogue of modelling pitfall checks over the data and fails a build on them;
* grades generated SHACL by what the profile knows, so the shapes never reject their own data;
* gives value ranges and per-language coverage per class and property;
* combines a per-query timeout, retries, a labelled fallback and exit codes that tell a script
  what happened;
* saves the raw profile with a published JSON Schema and regenerates every output from it without
  querying again.

== Where others go further

* *VoID.* SHACL Play, void-generator and LODStats write it; rdf-fingerprinter collects similar counts
  but does not write them as VoID.
* *Store speed.* void-generator reads Virtuoso through JDBC and has QLever query variants;
  rdf-fingerprinter gives that up for portability.
* *Files.* sheXer and QSE stream very large files; rdf-fingerprinter needs a store.
* *Resume.* void-generator writes its VoID as it goes and RDF2Graph records finished steps; an
  interrupted rdf-fingerprinter run starts again.
* *A whole SHACL toolchain.* SHACL Play also validates, documents shapes, filters them and converts
  them to JSON Schema, XSD and SPARQL.
* *Benchmarks.* QSE and sheXer publish experiments; rdf-fingerprinter has no comparative timings yet
  (the `benchmark-fingerprinter` change is a pitch).

== Neighbouring tools

* *SPARQL-LLM* (SIB, `pip install sparql-llm`) builds ShEx shapes from an endpoint's VoID
  description and retrieves them, with example queries, to help a model write SPARQL. The pattern
  schema serves the same purpose from a fingerprint, with statistics and labels.
* *OOPS!* (OntOlogy Pitfall Scanner) checks an ontology against its pitfall catalogue. The pitfall
  scan follows that catalogue where SPARQL can express it, and runs data checks against the
  instances too.
