= Schemas for LLMs
:description: The pattern schema (five files per graph) and the enriched ShExC: compact, labelled schemas of a fingerprinted graph for a language model that writes SPARQL.

A language model writes better SPARQL when it knows the shape of the data: which classes exist, which
properties link them, and what the values look like. The SHACL shapes say this, but at several times
the size. rdf-fingerprinter renders the same saved profile in compact forms for a model's context
window. For each graph with a class it writes six files: five for the pattern schema and one ShExC.

[cols="2,1,3"]
|===
| File | Form | Content and use

| `prefixes-<graph>.md` | Markdown table | each prefix, its namespace and how much of the schema uses it; read it to expand a prefixed name
| `patterns-<graph>.md` | Markdown | the triple-pattern lines `(:Class)-property-> (:Target)` with statistics, one fenced block per class; the file to give a model that writes SPARQL
| `patterns-<graph>.csv` | CSV | the same edges, one row per edge and one column per statistic; for a script, a filter or a spreadsheet
| `glossary-<graph>.md` | Markdown list | the labels and short descriptions of the terms, one line each; for a model that maps the words of a question to terms
| `glossary-<graph>.csv` | CSV | the full labels, alt labels, definitions and notes, one row per term and language
| `shex-<graph>.shex` | ShExC | the same content as ShEx shapes, the statistics in comments; every file parses with PyShExC
|===

Choose the part you give an agent. A model that writes SPARQL needs `patterns-<graph>.md` and
`prefixes-<graph>.md`. Add `glossary-<graph>.md` when users ask in words that differ from the term
names. A script that filters the schema, or a model with a tool to query it, reads the CSV files.
Nothing needs all six.

All are rendered from one <<pattern-view,pattern view>> of the profile, so they never disagree. Like
every xref:representations.adoc[representation], they are generated from `profile.json` alone and send
no query. A graph with no class gets no file.

== Generate

[source,bash]
----
fingerprint -e https://my.endpoint/sparql -o out --format pattern --format shex
fingerprint-gen-pattern out/profile.json -o llm/ --ontology vocab.ttl --max-classes 30
fingerprint-gen-shex    out/profile.json -o llm/ --min-instances 10
----

The two `fingerprint-gen-*` commands take the options every generator takes
(xref:representations.adoc#later-from-the-saved-profile[Representations]: `-o`, `--threshold`,
`--template`, `--prefixes`, `--exclude-namespace`, `--include-namespace`), plus:

[cols="1,3"]
|===
| `--ontology FILE` | an RDF file (Turtle, RDF/XML, TriG, N-Quads, … by its extension) whose labels, alt labels, descriptions and notes win over the profile's (<<labels,Labels and descriptions>>)
| `--min-instances N` | hide classes with fewer than N instances; N ≥ 1 (<<size-filters,Size filters>>)
| `--max-classes K` | show only the K largest classes; K ≥ 1
|===

`fingerprint --format pattern|shex` renders with the defaults: no ontology file and no size filter;
the labels come from the store (<<labels,Q12>>). An unreadable ontology file or a value below 1 is a
usage error (exit 2), and nothing is written.

Measured on the test profile (`tests/test_data/golden/`; `wc -m`, Unicode code points). The test
profile has no labels, so its glossaries are empty. With the label fixture
`tests/test_data/ontology/labels.ttl`, the `continents` glossary is 563 characters (Markdown) and 927

|===
| File | `continents` | `treaties`

| `prefixes-<graph>.md` | 768 | 907
| `patterns-<graph>.md` | 2,081 | 3,620
| `patterns-<graph>.csv` | 5,872 | 10,593
| `glossary-<graph>.md` (empty) | 128 | 126
| `glossary-<graph>.csv` (empty) | 62 | 62

The patterns Markdown is about five times smaller than the SHACL shapes of the same graph; with the
prefix file, about four times. The CSV is longer because it repeats the owner, the block and the
target kind on every row. It is for scripts, not for a context window.

== The pattern schema

=== The prefix file

`prefixes-<graph>.md` has one row per prefix of the names the patterns write, sorted by prefix. The
counts cover the patterns only: `classes` the distinct classes of the blocks and expanded nested
groups, `properties` the distinct properties of the edges, `instances` the instances of those classes,
`triples` the triples of those edges. A prefix used only for a datatype has four zeros. Three of the
nine rows of `prefixes-continents-214e8f67.md`:

[source,markdown]
----
# Prefixes of http://publications.europa.eu/resources/authority/continents

| prefix | namespace | classes | properties | instances | triples |
|---|---|---:|---:|---:|---:|
| dcterms | <http://purl.org/dc/terms/> | 0 | 3 | 0 | 310 |
| euvoc | <http://publications.europa.eu/ontology/euvoc#> | 2 | 3 | 12 | 322 |
| xsd | <http://www.w3.org/2001/XMLSchema#> | 0 | 0 | 0 | 0 |
----

=== The patterns Markdown

`patterns-<graph>.md` starts with a title, a line naming the two sibling files, the legend, and the
notes `Hidden: <n> classes.` and `Excluded namespaces: <note>.` when filters left something out
(<<size-filters,Size filters>>, <<excluding-namespaces,Excluding a namespace>>). Then comes one
`##` heading and one fenced `text` block per class group, by instances, largest first, then by name.
There are no prefix declarations and no glossary: they are in the sibling files. The first block of
`tests/test_data/golden/patterns-continents-214e8f67.md`:

[source,text]
----
(:euvoc:Continent&skos:Concept) 6
  -dcterms:created-> xsd:date =2014-10-10
  -euvoc:startDate-> xsd:date =1952-07-24
  -euvoc:status-> IRI d1
  -euvoc:xlNotation-> (:euvoc:XlNotation) bn
    -dcterms:created-> xsd:date =2014-10-10
    -dcterms:type-> IRI d1
    -euvoc:startDate-> xsd:date =1952-07-24
    -euvoc:status-> IRI d1
    -rdf:value-> xsd:string AFRICA..OCEANIA
  -skos:inScheme-> (:owl:Ontology&skos:ConceptScheme) d1
  -skos:topConceptOf-> (:owl:Ontology&skos:ConceptScheme) d1
  -skosxl:prefLabel-> (:skosxl:Label) ×24 bn
    -dcterms:created-> xsd:date =2014-10-10
    -dcterms:type-> IRI d1
    -euvoc:startDate-> xsd:date 1952-07-24..2014-10-10 d2
    -euvoc:status-> IRI d1
    -lvont:script-> IRI 12/145 d2
    -skosxl:literalForm-> rdf:langString @24
----

Read it as:

* `(:euvoc:Continent&skos:Concept) 6` — a *block*: 6 instances, each typed both classes (a
  xref:glossary.adoc#merged-group[merged group]). The arrows are SPARQL triple-pattern notation:
  `?c a euvoc:Continent ; skos:inScheme ?s . ?s a skos:ConceptScheme`.
* `-skosxl:prefLabel-> (:skosxl:Label) ×24 bn` — every continent has 24 labels, all blank nodes. The
  indented lines below it are the label nodes' own edges (a xref:glossary.adoc#nested-group[nested group]), with
  statistics over all 145 `skosxl:Label` instances: `12/145` of them have `lvont:script`.
* `owl:Ontology` is a meta class, hidden by default, yet it stays in the group name, because its
  group has the shown member `skos:ConceptScheme`.

=== Blocks and headers

A block header is `(:<group>) <instances>`, then:

[cols="1,3"]
|===
| ` ~<m> first_n` | the class was read in first-N mode; the statistics cover its first m instances
| ` co <class> <k>` | k instances are also typed `<class>`, which is not merged into the group
| ` via (:S)-p, …` | incoming links: the groups and properties that point at this group, by source then property
|===

=== Edges

An edge is two spaces per level, `-<property>-> <target>`, then its statistics. One edge per property,
by prefixed name. The target lists, joined by `|`:

. the object classes, by group name, inside one `(:…|…)`, hidden groups included; a class typed in
  another graph is written `(:ex:Person @<http://ex.org/people>)`;
. the literal datatypes; a language-tagged literal is `rdf:langString`, a plain one `xsd:string`;
. `IRI` for untyped IRI objects, `BNODE` for untyped blank nodes.

A property with no recorded values has the target `.`.

The statistics, each after one space, in this order:

[cols="1,3"]
|===
| Token | Meaning

| `k/n` | k of the n observed instances have the property; omitted when all do
| `×a`, `×a-b` | values per instance that has it, fewest to most; omitted when 1
| `bn` | some objects are blank nodes
| `@en`, `@24` | the one language, or the number of languages
| `=v` | one literal datatype, and every value is `v`
| `lo..hi` | one literal datatype, smallest and largest value
| `=prefix:local` | every object is the one IRI; only when the profile has top values (depth `rich_values` or deeper)
| `dN` | N distinct objects, fewer than the triples; omitted with `=v` or `=name`
| `presence` | found by the completeness check only; no other statistic
|===

A value is written bare when it is not empty and holds no white space, no `"` and no `..`. Otherwise,
or when it is longer than 64 characters, it is a JSON string, cut at 64 characters with `…`:
`="Treaty of Rome"`, `="1..2"`, `=""`.

=== Reified relations

A class with reified relations (links made through a reification, such as resources used as predicates
(singleton properties) or `rdf:Statement` nodes) ends its block with one line per relation, after its edges:

[source,text]
----
~> ex:Link (:ex:Org) 2 statements via resource_as_predicate [reifiers: rdf:singletonPropertyOf 2, prov:wasAttributedTo 1]
----

`-p->` is a triple in the data; `~>` is a link that exists only through a reifier node. The ShExC
carries the same line as a comment inside the shape. The notation, the kinds and the limits (a
`via negative_property_assertion` line is a denial) are in xref:reifications.adoc#notation[Reified
Relations]. The CSV and the glossary have no reified relation.

[#chains]
=== Nested blank nodes

A class whose instances are reached only as blank-node objects, and by enough of them to cover all its
instances, gets no block. Its edges are written under the edge that reaches it, one level deeper.
A hop is one edge; edges sit at levels 1 to 3, so the deepest chain is class → blank node → blank
node → target.

* Each nested group is expanded once, under the shallowest edge with the most triples into it
  (ties: source name, then property name). Every other edge into it ends ` ^`.
* An edge at level 3 into a group expanded nowhere ends ` …` (deeper than 3 hops).
* A blank-node cycle is expanded once; its edge back to itself ends ` ^`.

The statistics of a nested group are over all its instances, not per path.

[#csv]
== The CSV files

Both follow RFC 4180: a header row, UTF-8, `\n` line ends. An absent value is an empty cell; a flag is
`true` or `false`; a number is its digits. Several values in one cell are joined by ` | ` (space, bar,
space), the same separator everywhere. A cell with `,`, `"`, a line break or a leading or trailing
space is quoted with `"`, and a `"` inside it is doubled.

=== patterns-<graph>.csv

Per block, in the order of the Markdown: one block row, then one row per edge line, in line order.

[cols="1,3"]
|===
| Column | Content

| `graph` | the graph IRI; empty for the default graph
| `block` | the group name of the block the row sits in
| `owner` | the group whose profile gives the edge: the nested group for a nested edge
| `path` | the properties of the edges above it, joined by `/`; empty at depth 1
| `depth` | 0 for the block row, 1 to 3 for an edge
| `property` | the prefixed name of the property
| `targets` | the target alternatives, joined by ` \| `: a class group without `(:` and `)`, a datatype, `IRI` or `BNODE`
| `target_kinds` | the kind of each target: `group`, `datatype`, `iri`, `blank_node` or `unknown`
| `ending` | empty, `^` (expanded under another edge) or `…` (deeper than 3 hops)
| `instances` | the owner's observed instances
| `subjects` | the instances that have the property
| `triples` | its triples
| `per_min`, `per_max` | the fewest and most values per instance that has it
| `blank_nodes` | whether some objects are blank nodes
| `languages` | the language tags, sorted
| `min_value`, `max_value` | the lowest and highest value, as in `lo..hi` or `=v`; not cut and not quoted
| `single_value` | the value of `=v`, or the name of the IRI of `=<name>`
| `distinct` | the distinct objects
| `presence_only` | whether the completeness check found it and nothing else
| `first_n` | on a block row: the instances read in first-N mode
| `via` | on a block row: each incoming link as `<source>-<property>`
|===

A value the profile does not hold is an empty cell. The block row and one edge row of `continents`:

[source,text]
----
graph,block,owner,path,depth,property,targets,target_kinds,ending,instances,subjects,triples,per_min,per_max,blank_nodes,languages,min_value,max_value,single_value,distinct,presence_only,first_n,via
http://publications.europa.eu/resources/authority/continents,euvoc:Continent&skos:Concept,euvoc:Continent&skos:Concept,,0,,,,,6,,,,,,,,,,,,,
http://publications.europa.eu/resources/authority/continents,euvoc:Continent&skos:Concept,euvoc:Continent&skos:Concept,,1,euvoc:startDate,xsd:date,datatype,,6,6,6,1,1,false,,1952-07-24,1952-07-24,1952-07-24,1,false,,
----

=== glossary-<graph>.csv

One row per term and language, for each term the output uses that has a label, an alt label, a
description or a note. Sorted by prefixed name, then the untagged language first, then by tag.

[cols="1,3"]
|===
| Column | Content

| `term`, `iri` | the prefixed name and the full IRI
| `kind` | the <<kinds,kind codes>>, several joined by ` \| `
| `language` | the language tag; empty for untagged
| `pref_label` | the label in that language
| `alt_labels` | all alt labels in that language, in full, joined by ` \| `
| `definition` | the description in that language, in full
| `notes` | all notes in that language, in full, joined by ` \| `
|===

From the label fixture; `skos:Concept` has a German and an English row:

[source,text]
----
term,iri,kind,language,pref_label,alt_labels,definition,notes
skos:Concept,http://www.w3.org/2004/02/skos/core#Concept,C,de,,Begriff,,
skos:Concept,http://www.w3.org/2004/02/skos/core#Concept,C,en,Concept,Notion,An idea or notion; a unit of thought.,Also a SKOS class. | Use for concepts of a scheme.
skosxl:prefLabel,http://www.w3.org/2008/05/skos-xl#prefLabel,oP,en,preferred label,,,
----

[#kinds]
=== Kind codes

[cols="1,3"]
|===
| Code | The term is

| `C` | a class
| `dP` | a property whose objects are literals
| `oP` | a property whose objects are IRIs, classes or blank nodes
| `P` | a property with no collected objects
| `D` | a datatype
|===

A term with several codes lists them in the order `C`, `dP`, `oP`, `P`, `D`: joined by ` | ` in the CSV,
by `/` in the Markdown.

=== Filtering a CSV

Any tool that reads CSV works. Two one-liners on the continents file:

[source,bash]
----
# every row that mentions skosxl:Label (a row is one line)
grep -F 'skosxl:Label' patterns-continents-214e8f67.csv

# the blank-node edges of depth 1, most triples first (DuckDB)
duckdb -c "SELECT block, property, triples FROM 'patterns-continents-214e8f67.csv'
           WHERE depth = 1 AND blank_nodes ORDER BY triples DESC"
----

`grep` also matches the `block` and `owner` columns; use DuckDB or csvkit when a column matters.

== The enriched ShExC

The same view as ShEx Compact Syntax, for tools and models that know ShEx. The block header becomes a
comment, each edge a triple constraint with its cardinality, and the statistics a comment after it.
From `tests/test_data/golden/shex-continents-214e8f67.shex` (prefixes left out):

[source,shex]
----
# comments use the pattern schema's legend: k/n instances having p (omitted: all) · ×a-b values per instance (omitted: 1) · bn blank nodes · @n languages, @tag one language · =v one value · lo..hi range · dN distinct values (omitted: all differ) · presence found, not measured · … deeper than 3 hops
# (:euvoc:Continent&skos:Concept) 6
euvoc:Continent {
  dcterms:created xsd:date ;  # =2014-10-10
  euvoc:startDate xsd:date ;  # =1952-07-24
  euvoc:status IRI ;  # d1
  euvoc:xlNotation BNODE {  # (:euvoc:XlNotation) bn
    dcterms:created xsd:date ;  # =2014-10-10
    dcterms:type IRI ;  # d1
    euvoc:startDate xsd:date ;  # =1952-07-24
    euvoc:status IRI ;  # d1
    rdf:value xsd:string ;  # AFRICA..OCEANIA
  } ;
  skos:inScheme @skos:ConceptScheme ;  # (:owl:Ontology&skos:ConceptScheme) d1
  skos:topConceptOf @skos:ConceptScheme ;  # (:owl:Ontology&skos:ConceptScheme) d1
  skosxl:prefLabel BNODE @skosxl:Label {24} ;  # (:skosxl:Label) ×24 bn
}
# (:owl:Ontology&skos:ConceptScheme) 1 via (:euvoc:Continent&skos:Concept)-skos:inScheme, (:euvoc:Continent&skos:Concept)-skos:topConceptOf
skos:ConceptScheme {
  dcterms:created xsd:date ;  # =2014-10-10
  dcterms:identifier xsd:string ;  # =http://publications.europa.eu/resource/authority/continent
  euvoc:startDate xsd:date ;  # =2014-10-10
  euvoc:status IRI ;
  owl:imports IRI ;
  rdfs:comment rdfs:Literal ;  # =Continent
  skosxl:prefLabel BNODE @skosxl:Label ;  # (:skosxl:Label) bn
}
# (:skosxl:Label) 145
skosxl:Label BNODE {
  dcterms:created xsd:date ;  # =2014-10-10
  dcterms:type IRI ;  # d1
  euvoc:startDate xsd:date ;  # 1952-07-24..2014-10-10 d2
  euvoc:status IRI ;  # d1
  lvont:script IRI ? ;  # 12/145 d2
  skosxl:literalForm rdf:langString ;  # @24
}
# glossary: none
----

[cols="1,3"]
|===
| Pattern view | ShExC

| block | `# ` + the header, then a shape named after the group's first shown member
| edge | `<property> <value> <cardinality> ;`, then `  # <comment>` when the comment is not empty: the target text when it names a class group, the statistics, and `… deeper than 3 hops` where the pattern has ` …`
| value | a group with a shape in the file → `@<shape>`; any other class (hidden, from another graph, not profiled) → `IRI`; a datatype as is; several → `(a OR b)`
| cardinality | exactly 1 → nothing; 0–1 → `?`; exactly a > 1 → `\{a}`; else `{a,b}`; no histogram → `*`
| nested group reached by one edge | inline: `p BNODE { … } ;`
| nested group reached by more edges | one `<label> BNODE { … }` shape after the block shapes, referenced as `BNODE @<label>`
| nested group expanded nowhere | `BNODE`, no shape
| glossary | each line commented with `# `
|===

The cardinalities record what was observed. PyShExC rejects `=` in an IRI, so a class or property whose IRI holds `=` is left out of
the ShExC and listed on a `# skipped:` line; the pattern schema keeps it as `<IRI>`.

[#labels]
== Labels and descriptions

A model maps a question's words to terms through their labels. Each class and property can carry
labels, alt labels, descriptions and notes, from two sources:

. **The store.** At every depth from `classes` on, the collector sends one query per graph (Q12,
  xref:statistics.adoc[Statistics]) for the annotations of the graph's classes and, from depth
  `properties`, of its properties. It looks in the default graph and in every named graph, so an
  ontology loaded in its own graph counts. The selected values are saved in `profile.json`
  (`term_annotations`).
. **An ontology file**, `--ontology FILE`, read when generating.

The predicates:

[cols="1,3"]
|===
| Label, in priority order | `skos:prefLabel`, `skosxl:prefLabel`/`skosxl:literalForm`, `rdfs:label`, `dcterms:title`
| Alt label | `skos:altLabel`, `skosxl:altLabel`/`skosxl:literalForm`; all are kept, and none becomes a label
| Description, in priority order | `skos:definition`, `rdfs:comment`, `dcterms:description`
| Note | `skos:scopeNote`, `skos:note`, `skos:example`, `skos:editorialNote`, `skos:historyNote`, `skos:changeNote`, and every description that was not selected
|===

The definition says what the term means. A note says how to use it or what to watch for: a
`skos:scopeNote` is a note, not a definition. Only literals count. For each language (untagged counts
as one), the label and the description come from the first predicate that has one in that language;
among several, the smallest text wins.

Per term and per field (labels, alt labels, descriptions, notes), the ontology file's values win when
it has any, else the store's; the two are never mixed. A term labelled `"Persoon"@nl` with the
description `"Iemand"@nl` in the store, and `"Person"@en` with no description in the ontology, shows
as `ex:Person C "Person"@en: Iemand`.

The glossary Markdown lists, by name, every term the patterns use that has a label, an alt label or a
description. One line each: the name, the kind code, the label, the alt labels in the language of the
label, the description. It shows one language: the untagged value, else `en`, else the smallest tag.
A term with no label shows an alt label in its place. A description is put on one line and cut at 200
characters with `…`. Notes are not in the Markdown; they are in the CSV, in full. With the test
fixture, `glossary-treaties-3b4301a8.md` is:

[source,markdown]
----
# Glossary of http://publications.europa.eu/resources/authority/treaties

- dcterms:created dP "Date Created"@en: Date of creation of the resource.
- dcterms:type oP: A long description, longer than two hundred characters, so that the glossary has to shorten it: it goes on about the nature or genre of the resource, recommends a controlled vocabulary, and repeats it…
- euvoc:Treaty C "Vertrag"@de
- skos:Concept C "Concept"@en alt: "Notion": An idea or notion; a unit of thought.
- skosxl:Label C "Label"@en: A special class of lexical entities.
- skosxl:altLabel oP "alternative label"@en
- skosxl:prefLabel oP "preferred label"@en
----

Without annotations it says `No term of this graph has a label or a description.` and the CSV holds
only its header. A profile saved before 3.2 has no `term_annotations` and renders that way. The ShExC
ends with the same lines, each after `# `.

[#size-filters]
== Size filters

A large store can have hundreds of classes. The size filters keep the file within a context window.
They apply after the xref:representations.adoc#filters[namespace filters], to named groups:

* `--min-instances N` hides groups with fewer than N instances;
* `--max-classes K` then keeps the K groups with the most instances (ties by name).

A hidden group gets no block and leaves `via` lists, but is still named as an edge target, so no link
is lost. The patterns Markdown says how many classes it hides. On the test profile, `--min-instances 2` hides
the scheme (`owl:Ontology` and `skos:ConceptScheme`) of `treaties`, and `patterns-treaties-3b4301a8.md` holds:

[source,text]
----
Hidden: 2 classes.
----

The edge `-skos:inScheme-> (:owl:Ontology&skos:ConceptScheme) d1` still names the hidden scheme. There
is no `(:owl:Ontology&skos:ConceptScheme)` block, and the CSV has no row for it.

Nested groups are never hidden by size; they show wherever a shown block reaches them.

[#excluding-namespaces]
== Excluding a namespace

A size filter hides classes; `--exclude-namespace` leaves out every term of a namespace: its
classes, its edges and `via` entries, its glossary lines and its prefix row
(xref:representations.adoc#filters[Namespace filters]). It is the tool for a namespace of
generated terms that crowds the file. The brainframe workspace graph, for example, models each relation
as an RDF singleton property `relationid:<uuid>`: 619 distinct properties, which fill more than half of
its pattern file.

[source,bash]
----
fingerprint-gen-pattern profile.json -o llm/ --exclude-namespace relationid
fingerprint-gen-shex    profile.json -o llm/ --exclude-namespace relationid
----

The patterns Markdown says what it left out, in one line near the top:

[source,text]
----
Excluded namespaces: relationid (classes 0, properties 619, values 0).
----

(The ShExC has `# excluded namespaces: …`.) Filters combine: repeat the option, name several
namespaces at once by an IRI stem or a prefix glob, and bring one back with `--include-namespace`
(it wins over an exclude):

[source,bash]
----
# four prefixes
fingerprint-gen-pattern profile.json -o llm/ --exclude-namespace relationid \
  --exclude-namespace foaf --exclude-namespace prv --exclude-namespace dcterms
# every instance namespace under one IRI stem
fingerprint-gen-pattern profile.json -o llm/ --exclude-namespace 'https://my.brainframe.com/#/knowledge/'
# the same, keeping one of them
fingerprint-gen-pattern profile.json -o llm/ --exclude-namespace 'https://my.brainframe.com/#/knowledge/' \
  --include-namespace document
----

The statement nodes of those relations are typed `brainframe:RelationId`, in the same namespace as
the real classes, so a namespace filter cannot hide them.

Excluding drops those links. A predicate with a non-property type, such as the
`brainframe:RelationId` singletons, need not be excluded: by default the fingerprint folds it into a
`~>` line of its subject's class, named by that type
(xref:reifications.adoc[Reified Relations]). Predicates typed only `rdf:Property` are not recognised;
exclude their namespace as above.

[#pattern-view]
== The pattern view

All the files are layouts of one pattern view per graph (`PatternGraph` in
`fingerprint/domain/views.py`, built by `fingerprint/domain/patterns.py`; the ShExC view `ShexSchema`
by `fingerprint/domain/shex.py`). A custom template package (`--template`,
xref:representations.adoc#your-own-templates[Your own templates]) receives that view as `view`, once
for each of the five pattern files of a graph: it is a `PatternFile` (the kind of file, plus the
graph's view). A package written for the single `pattern-<graph>.txt` of 3.3 must now render the
five. The
view is built from the profile's analytics and term annotations only, and is deterministic: the same
profile gives the same files.

The view's terms (pattern view, merged group, nested group, term annotation) are defined in the
xref:glossary.adoc#llm-schemas[glossary].

from fingerprint.domain.views import GeneratorOptions
