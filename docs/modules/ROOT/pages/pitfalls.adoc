= Pitfalls
:description: Scan a fingerprinted store for modelling pitfalls: OOPS!-style schema checks and data checks, in SPARQL.

The fingerprint says what a dataset holds. The pitfall scan says what is wrong with how it is
modelled: relations used but never defined, classes declared twice under one label, properties with
two domains, individuals used as predicates. It runs in the same pass, against the same endpoint,
and the findings land next to the profile.

[source,bash]
----
fingerprint -e https://my.endpoint/sparql -o out --pitfalls --schema-graph https://ex.org/graph/ontology \
            --format pitfalls --fail-on critical
----

== What runs

Each check is one SPARQL `SELECT` file. With `--pitfalls`, every profiled graph is scanned after it is
profiled, at any `--depth`:

* **Without `--schema-graph`**, every check runs over each graph alone.
* **With schema graphs** (`--schema-graph`, repeatable), each schema graph is profiled too, and it
  runs the `schema` checks on its own. Every other graph runs the `data` checks over itself joined
  with the schema graphs (`FROM <graph> FROM <schema>`), so "is this relation declared?" looks in the
  ontology.
* A graph with no triple is not scanned.

For each check the scan sends two queries, a count and the first `--pitfall-examples` rows (default
10, ordered). Results are saved in `profile.json` with the check's metadata and the time it took.

The scan is off by default, because several checks scan every triple. A check that times out is a
recorded failure (exit 1), like any other failed measurement.

== Where the findings show

[cols="1,3"]
|===
| Report page | A *Pitfalls* section: checks with findings per importance, one entry per check with its examples as short names, and the checks that found nothing. A class named by a check gets a badge linking to it. The search box filters the checks too.
| `--format pitfalls` | `pitfalls-<graph>.tsv` per scanned graph, in ROBOT's report columns (`Level`, `Rule Name`, `Subject`, `Property`, `Value`; critical → `ERROR`, important → `WARN`, minor → `INFO`). `fingerprint-gen-pitfalls profile.json -o dir` writes it again offline.
| `--fail-on LEVEL` | Exit 5 when the run recorded no failure and a check of importance `LEVEL` or higher (`critical` > `important` > `minor`) found something. Useful in CI.
|===

== Options

[cols="1,1,3"]
|===
| Option | Default | Meaning

| `--pitfalls` | off | Run the scan (setting `pitfall_scan`, `RDF_FINGERPRINTER_PITFALL_SCAN`).
| `--schema-graph IRI` | none | A graph holding the ontology (repeatable; `RDF_FINGERPRINTER_SCHEMA_GRAPHS`, comma-separated).
| `--pitfall-examples N` | 10 | Example rows kept per check and graph.
| `--pitfall-checks DIR` | — | Your own `.rq` checks, added to the catalogue; one with a packaged id replaces it.
| `--skip-pitfall ID` | — | Leave a check out (repeatable).
| `--fail-on LEVEL` | — | `critical`, `important` or `minor`; see above.
|===

`--pitfall-checks`, `--skip-pitfall` and `--fail-on` need `--pitfalls`.

== Writing a check

A check is a SPARQL `SELECT` of exactly `?entity ?property ?value`, one row per finding, after a header
of comment lines:

[source,sparql]
----
# id: my_untyped_subject
# title: Subject without a type
# importance: minor
# scope: data
# source: my team
# description: optional, one line
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
SELECT ?entity ?property ?value WHERE {
  ?entity ?p ?o . FILTER NOT EXISTS { ?entity rdf:type ?t }
  BIND(rdf:type AS ?property) BIND("no rdf:type" AS ?value)
}
----

Rules:

* The required keys are `id` (`[a-z0-9_]+`), `title`, `importance`, `scope` and `source`; the optional
  ones are `heuristic` (`true`/`false`) and `description`. An unknown or repeated key is refused, and
  `#` lines without a key are comments.
* Each `PREFIX` or `BASE` goes on its own line before the `SELECT`.
* There is no `FROM`: the scan sets the dataset.
* Only `SELECT` is accepted; anything else is refused before any query (exit 2).

The same files work with ROBOT: `robot report --profile p.txt`, where each line of `p.txt` is
`LEVEL<TAB>file:./check.rq`.

== The catalogue

Most checks follow the https://oops.linkeddata.es/catalogue.jsp[OOPS! pitfall catalogue] (its codes
are in the *Source* column); the `x_` checks are the fingerprinter's own. Heuristic checks judge by
names and are hints. The domain and range checks read the declared schema closed-world: OWL would
infer a type rather than report an error.

== Scan files

To scan RDF files rather than an endpoint, `make scan-files ONTOLOGY=o.owl [DATA=d.rdf] OUT=dir` loads
them into a separate in-memory Oxigraph (port `RDF_FINGERPRINTER_SCAN_PORT`, default 7880; the e2e
test store is never touched) and runs the scan over them. Extra options go in `SCAN_ARGS`.
