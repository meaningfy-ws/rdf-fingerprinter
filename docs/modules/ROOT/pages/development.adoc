= Development

Requires Poetry, Docker, and Node.js (for `make check-spec` and the docs).

[source,shell]
----
make install                    # Poetry env with the test and lint groups
make check-all                  # lint, types, layers, OpenSpec, unit tests — the gate CI runs
make oxigraph-load-test-data    # in-memory Oxigraph on :7878 with the test graphs
make test-e2e                   # end-to-end tests against it (local only)
make check-mutation             # mutation score ratchet (about 1 h)
make build                      # sdist + wheel, checks the templates are in the wheel
make preview-docs               # build this site and serve it on :8088
----

[#tests]
== Tests

Every check has one home. The rules below say where a test goes, what it may import, which data it
uses and what the gate demands. `make check-architecture` and the guards in `tests/guards/` enforce
them.

[#test-tiers]
=== Tiers: where a new test goes

[cols="2,2,3"]
|===
| The check is about… | Put it in | Example

| what a user of a capability sees (a spec scenario)
| a scenario in `tests/features/<capability>.feature`; steps in `tests/bdd/steps/`
| "No queries during rendering"

| a rule that holds for all inputs
| `tests/unit/domain/`, as a Hypothesis property (strategies in `tests/unit/domain/strategies.py`)
| prefix compaction round-trips

| a branch or error path no scenario reaches
| `tests/unit/<layer that decides>/` (`domain`, `adapters`, `service_layer`, `entrypoints`)
| HTTPS→HTTP prefix-fetch fallback

| the exact text or graph of a generated output
| `tests/unit/service_layer/test_representations_golden.py`
| `shapes-continents-*.ttl`

| talking to a real SPARQL store
| `tests/e2e/`
| first-N reads at most N instances

| the repository itself (packaging, dicts, traceability, fences, wiring)
| `tests/guards/`
| the wheel contains the templates
|===

A test that repeats an assertion another tier owns is deleted. Unit test files are named after the
module they test: `tests/unit/<layer>/test_<module>.py`. Every test directory is a package (it has
an `__init__.py`).

Shared support lives at the top of `tests/`:

[cols="1,3"]
|===
| File | Holds

| `conftest.py` | The sample-data fixtures, the Hypothesis profiles, the no-network and no-prefix-lookup fixtures.
| `sample_data.py` | The facts about the canonical datasets; `same_profile()` and `differences()`.
| `builders.py` | Builders of model objects for edge cases.
| `fakes.py` | `FakeSparql` (an in-memory rdflib store) and other test doubles.
| `bdd/conftest.py` | The shared step library: imports every `tests/bdd/steps/<area>.py`.
|===

[#test-traceability]
=== Traceability: every spec scenario has one test

`tests/guards/test_traceability.py` checks that every `#### Scenario: <title>` in
`openspec/specs/<capability>/spec.md` has a Gherkin scenario with the *same title* in
`tests/features/<capability>.feature` (`-` in the capability becomes `_`). Titles compare after
stripping surrounding spaces. The guard fails on:

* a spec scenario with no feature scenario and no allow-list entry;
* a feature scenario whose title is in no spec scenario of that capability;
* a title used twice in one spec or one feature file;
* a malformed or stale allow-list entry.

When titles differ, rename the feature scenario. The spec is the truth; change it only through a
spec delta in an OpenSpec change.

Add an allow-list entry only when a scenario is about the repository, not the product, and a
pytest test proves it. Entries go in `tests/guards/untraced_scenarios.txt`, one per line, `#`
starts a comment:

----
<capability> | <scenario title> | <path>::<function> | <reason>
----

The node id names a plain module-level test function: no class, no parametrisation suffix, no
make target. The guard parses the file and checks the function exists. A check that is a make
target gets a thin pytest wrapper that runs the tool in a subprocess.

[#test-fences]
=== Fences

`.importlinter` lists `fingerprint` and `tests` as root packages and fences the test tiers.
Indirect imports count.

[cols="2,3"]
|===
| Source | May not import

| `tests.unit.domain` | `fingerprint.adapters`, `fingerprint.service_layer`, `fingerprint.entrypoints`, `tests.fakes`
| `tests.unit.adapters` | `fingerprint.service_layer`, `fingerprint.entrypoints`
| `tests.unit.service_layer` | `fingerprint.entrypoints`
| `tests.builders`, `tests.sample_data` | `fingerprint.adapters`, `fingerprint.service_layer`, `fingerprint.entrypoints`
| `tests.conftest`, `tests.sample_data`, `tests.builders`, `tests.fakes` | any test tier
| `tests.unit`, `tests.bdd`, `tests.e2e`, `tests.guards` | each other (independence contract)
|===

No network outside `tests/e2e/`: an autouse fixture makes `socket.socket.connect` raise
`RuntimeError("network access is not allowed outside tests/e2e/")`. Use `FakeSparql` instead, or
move the test to `tests/e2e/`. Another autouse fixture sets `RDF_FINGERPRINTER_PREFIX_LOOKUP=false`.

[#test-data]
=== Canonical data

One sample dataset serves every tier: the continents and treaties RDF in `tests/test_data/`, and
the profile collected from it, `tests/test_data/profiles/sample-profile.json`.

* Assert the named facts in `tests/sample_data.py`, never a bare number. `CONTINENTS` and
  `TREATIES` give the graphs, the classes with their instance counts, and each class's properties
  with min and max cardinality. They are typed in by hand from the RDF;
  `tests/guards/test_sample_data.py` checks they agree with the stored profile.
* Use the session fixtures from `tests/conftest.py`: `sample_run` (the stored `ProfileRun`),
  `sample_analytics` and `sample_outputs` (every generator's files).
* Build an edge case locally, never in the canonical dataset: with the builders in
  `tests/builders.py` (`klass`, `prop`, `literals`, `resources`, `failure`, `profile_run`) or with
  `sample_run.model_copy(update=…)`.

Never edit the sample profile or a golden file by hand. Regenerate them:

[cols="1,3"]
|===
| Target | Run it when

| `make refresh-sample-profile`
| the RDF in `tests/test_data/` or the collector changed, or the drift test in `make test-e2e`
fails. Needs `make oxigraph-load-test-data`. Leaves the file untouched when nothing changed and
prints the classes and properties that differ. Update `tests/sample_data.py` if the data changed
on purpose.

| `make refresh-golden`
| a generator or template changed its output on purpose. Writes only the files in
`tests/test_data/golden/` that changed; review the diff.
|===

Turtle golden files compare as graphs (`rdflib.compare.isomorphic`); a failure prints the triples
only in the golden and only in the output. PlantUML and HTML golden files compare as text.

[#test-gate]
=== The gate

[cols="1,3"]
|===
| Command | Checks

| `make test-fast` (in `make check-all` = `make check-all-fast`, and CI)
| `tests/` without `tests/e2e/` and without the Hypothesis property tests; writes `coverage.xml`
for Codecov, with no coverage floor.

| `make test` (in `make check-all-deep`; weekly and on demand in CI, `deep.yml`)
| `tests/` without `tests/e2e/`, with branch coverage: at least 90% of `fingerprint/` and 100% of
`fingerprint/domain/` (the generated `profile.py` and `views.py` excluded). Hypothesis runs with
the `ci` profile (derandomized, no deadline).

| `make test-e2e` (local, before a release)
| `tests/e2e/` against the store at `RDF_FINGERPRINTER_TEST_ENDPOINT` (default
`http://localhost:7878/query`, the Oxigraph from `make oxigraph-load-test-data`). Includes the drift
test: a live collection must equal the sample profile.

| `make check-mutation` (about 1 h; weekly CI and on demand, locally before a PR)
| mutmut over `fingerprint/domain/` and `fingerprint/service_layer/`. The score,
(killed + timeout) / all counted mutants, must not fall below `tests/guards/mutation_score.txt`. A
drop exits 1 and lists the surviving mutants; a rise rewrites the file: commit it. A score raised by
the weekly CI run is not committed automatically; a developer commits it after a local
`make check-mutation`.
|===

Locally, Hypothesis uses the `dev` profile (random, no deadline); pass
`--hypothesis-profile=ci` to reproduce CI. Point `RDF_FINGERPRINTER_TEST_ENDPOINT` at any other store
loaded with `tests/test_data` to run the e2e tests there.

A branch that only a contrived test could reach gets `# pragma: no cover — <reason>`, never inside
`fingerprint/domain/`.

[#test-profile]
=== Which tests to run when: the tier profile

Each tier was run on its own with branch coverage (12-core laptop, 2026-11-02, Hypothesis `ci`
profile). Times are pytest's own and include the coverage overhead, which roughly doubles a run.
"Own layer" is the coverage of the layer the tier targets; "package" is all of `fingerprint/`.

[cols="2,1,1,2,1"]
|===
| Tier | Tests | Time | Own layer | Package

| `tests/unit/domain` (no Hypothesis) | 455 | 2 s | domain 89% | 61%
| `tests/unit/adapters` | 160 | 11 s | adapters 93% | 45%
| `tests/unit/service_layer` | 396 | 139 s | service_layer 99% | 90%
| `tests/unit/entrypoints` | 35 | 6 s | entrypoints 87% | 80%
| all of `tests/unit` (no Hypothesis) | 1,046 | 159 s | — | 93%
| `tests/bdd` (+ 4 `manual`, skipped) | 314 | 159 s | — | 94%
| `tests/guards` | 153 | 10 s | structure, not behaviour | 43%
| Hypothesis properties (`-m hypothesis`) | 18 | 37 s | domain 58% | 55%
| `make test-fast` (unit + bdd + guards) | 1,518 | 152 s, 318 s with coverage | domain 100% | 99%
| `make test-e2e` (needs the store) | 91 | 16 s | — | 73%
| `make check-mutation` | thousands of mutants | about 1 h | domain + service_layer | —
|===

What the numbers say:

* *The fast suite already carries the coverage.* Without Hypothesis it reaches 100% branch
  coverage of `fingerprint/domain/` and 99% of the package. The 18 property tests add no covered
  line; they add inputs nobody wrote down. That is why they belong to the deep session, not the
  quick one.
* *Two tiers carry the time.* `tests/unit/service_layer` and `tests/bdd` take about 2.5 minutes
  each; everything else together takes under 40 seconds. They also overlap: each covers 93–94% of
  the package alone.
* *One check costs a third of the fast suite.* "The shapes report no violation on their own data"
  validates the treaties graph against its SHACL shapes: 56 s in
  `tests/unit/service_layer/test_representations_golden.py` (three thresholds) and 18 s more as its
  Gherkin scenario in `tests/bdd`. Moving the three-threshold parametrisation to the deep gate
  would cut the fast suite by about a quarter.
* *Coverage doubles the run.* `make test-fast` takes 2.5 minutes, the same tests under coverage
  5.3 minutes. The quick gate still collects it, without a floor, because CI reports it to Codecov
  on every PR; the floors (90% package, 100% domain) stay in `make check-all-deep`.
* *Guards are cheap and catch structural mistakes* (layer fences, composed dicts, traceability,
  packaging) that no behaviour test sees; run them in every session.

So, by session:

[cols="1,2,3"]
|===
| Session | Run | Why

| While coding (seconds)
| `poetry run pytest tests/unit/<layer>` or the one test file you are changing, plus
`poetry run pytest tests/guards`
| The domain, adapters and entrypoints tiers finish in seconds and cover their own layer at
87–93%. In `tests/unit/service_layer`, add `-k "not shapes_report_no_violation"` to skip the
74-second SHACL check until the end.

| Before a commit or push (about 3–4 min)
| `make check-all` (= `make check-all-fast`)
| Static checks plus all 1,518 fast tests: 99% of the package is exercised. CI runs the same gate.

| Deep QA, before a release or after a domain change (10+ min, does not block a PR)
| `make check-all-deep`, then `make oxigraph-load-test-data` and `make test-e2e`
| Adds the Hypothesis properties, the coverage gates (90% package, 100% domain) and the real
store, including the sample-profile drift test.

| Weekly or before a large refactor (about 1 h)
| `make check-mutation`
| Checks that the tests would catch a wrong line, not just run it.
|===

[#test-properties]
=== Property tests with Hypothesis

An ordinary test checks one example you chose. A property test states a rule that must hold for
every input, and lets Hypothesis hunt for an input that breaks it. You write the rule. Hypothesis
plays the opponent.

Take the rule "the minimum is never above the mean, and the mean never above the maximum". An
example test checks it for one histogram. The property test in `tests/unit/domain/test_properties.py`
checks it for every histogram Hypothesis can build:

[source,python]
----
@given(histograms())
def test_cardinality_statistics_are_ordered_min_mean_max(case):
    observed, histogram = case
    stats = cardinality_statistics(histogram, observed)
    assert stats.min <= stats.mean <= stats.max
----

Where do the inputs come from? From the _strategies_ in `tests/unit/domain/strategies.py`, recipes
that build believable domain objects rather than random noise. `histograms()` makes bins whose
subjects never add up to more than the observed instances. `prefix_tables()` nests some namespaces
inside others, because that is where prefix matching goes wrong. `raw_iris` is the exception: it is
any text at all, junk included, to attack `to_iriref`. The strategies build their objects with
`tests/builders.py` and import only from `fingerprint.domain`, per the fences above.

When a rule breaks, Hypothesis _shrinks_ the input: it simplifies the failing case step by step and
reports the smallest one that still fails. You read "one bin, zero subjects", not forty random bins.

The properties cover the domain only, because that is where the rules live. Today they state five:
prefix compaction round-trips, the longest matching namespace wins, cardinality statistics are
ordered, every analytics ratio lies in [0, 1], and `to_iriref` returns a valid IRIREF or raises.
Add one when you find a rule that must hold for all inputs; a single tricky case is an ordinary unit
test.

The two profiles in `tests/conftest.py` trade discovery against repeatability. `dev`, the local
default, draws fresh inputs on every run, so each run can find something new. `ci`, used by
`make test` and mutmut, is derandomised: the same inputs every time, so a failure reproduces and a
killed mutant stays killed. Neither has a deadline, so a slow machine does not fail a test.

[#test-mutation]
=== Why mutation testing, and why it takes an hour

Coverage tells you a line ran during a test. It does not tell you a test would notice if that line
were wrong. Mutation testing closes that gap: it checks the tests, not the code.

Think of mutmut as a saboteur. It plants one small bug in a copy of the code, then runs the tests
against it. Take `fingerprint/domain/analytics.py`, which marks a property functional when no
instance has more than one value:

[source,python]
----
is_functional=max(bins) <= 1
----

The saboteur turns `<=` into `<`. If some test feeds in a property with exactly one value per
instance, that test now fails and the bug is caught: the mutant is _killed_. If every test only
uses properties with zero or several values, all tests still pass and the mutant _survives_. A
survivor points to a behaviour no test pins down, even though coverage marks the line as covered.

So why does it take an hour? Because each mutant needs its own test run. mutmut makes one for
every operator, comparison, number, boolean and string it can change in `fingerprint/domain/` and
`fingerprint/service_layer/`, which comes to thousands. For each one it runs the `tests/unit` and
`tests/bdd` tests that exercise the mutated function, Hypothesis properties included. A mutant that
causes an endless loop costs a full timeout before it counts as killed. A second or two per mutant,
times thousands of mutants, makes the hour.

That cost is why the check stays out of `make check-all` and runs weekly instead. It does not
guard each change. It guards the guards: the score in `tests/guards/mutation_score.txt` only
rises, so the suite can never quietly lose its teeth.

[#test-anti-patterns]
=== Anti-patterns

[cols="1,1"]
|===
| Don't | Do instead

| Assert a bare number from the sample data (`== 7`) | Assert the named fact from `tests/sample_data.py`
| Add an edge case to the canonical dataset | Derive it with a builder or `model_copy`
| Test one behaviour in Gherkin and in a unit test | Keep it in the tier the table above names
| Write a contrived test for a defensive branch | `# pragma: no cover — <reason>` (outside `domain/`)
| Edit a golden file or the sample profile by hand | `make refresh-golden` / `make refresh-sample-profile`
| Rename a spec scenario to match a test | Rename the feature scenario to match the spec
| Lower `mutation_score.txt` | Add the missing test or delete the dead code
| Import `tests.fakes` from a domain test | Build domain inputs with `tests.builders`
| Allow-list a scenario with a make target | Name a pytest test; add a thin wrapper if needed
|===

== Layout

[cols="1,3"]
|===
| Path | Holds

| `fingerprint/service_layer/handlers.py` | Report generation (the API).
| `fingerprint/entrypoints/cli/main.py` | The `fingerprint` CLI (click).

Layers are enforced by import-linter: `entrypoints` may import `service_layer`, never the reverse.

== Branches

`master` is the default and release branch; `develop` is the integration branch. A feature branch
starts from `develop` and is merged into it by pull request. A release is a pull request into
`master`; the tag is set on `master`, and `develop` is then brought level with `master`. Neither
branch takes direct commits, and CI runs the gate on pull requests into both.

== Releasing

. Update `version` in `pyproject.toml` and the `CHANGELOG.md`.
. Run `make check-all` and `make test-e2e`.
. Merge the release into `master` by pull request, then bring `develop` level with `master`.
. Publish a GitHub Release tagged `X.Y.Z` (no `v` prefix). The `publish` workflow runs the gate, builds, and
uploads to PyPI with Trusted Publishing (no token).

Docs deploy to GitHub Pages on every merge to `master` that touches `docs/`.
